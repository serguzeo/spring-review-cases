# Код-ревью. Ключ интервьюера

Нумерация строк Java начинается с первого `import`. Пустые строки и комментарии после него входят в счёт.

На 40 минут возьмите два файла. Основная пара — резервирование товара и история заказов. Более короткая пара — импорт прайс-листа и расчёт счёта. Подтверждение отгрузки можно поставить вместо одного из основных кейсов, если хотите обсудить сбои между сервисами.

Отправьте кандидату только выбранные `.java`-файлы и дайте 3–5 минут на чтение. Можно начать с задания.

> Представьте, что это изменение в PR. Какие замечания вы оставите? Начните с тех, которые блокируют мерж. Для каждого опишите, когда проявится проблема, как её исправить и как проверить исправление.

## Резервирование товара

Файл кандидата — `StockReservation.java`.

### Суть кейса

Склад должен уменьшить доступный остаток и создать резерв одной транзакцией. Повтор того же запроса должен вернуть уже созданный резерв без второго списания. `requestId` уникален в пределах клиента, сервис работает в нескольких экземплярах.

`reserve` сначала ищет резерв по паре `(customerId, requestId)`. Если его нет, метод читает остаток, проверяет количество, пишет вычисленный в Java новый остаток и вставляет резерв. При последовательном выполнении этот путь соблюдает контракт. На ревью нужно проверить те же шаги для двух одновременных запросов.

### Что не так

1. **Два покупателя могут получить последний товар.** Оба запроса с разными ключами читают остаток `1` и проходят проверку. Первый записывает `0`, создаёт резерв и коммитится. Второй ждёт блокировку на `UPDATE`, затем тоже записывает заранее вычисленный `0` и создаёт свой резерв. В БД остаток `0` и два резерва на одну единицу. `CHECK (available >= 0)` выполняется, а наличие транзакции при `READ COMMITTED` само по себе не защищает чтение от этой гонки. Чтение остатка — строка 44. Запись остатка — строка 50.

   Исправление — атомарное списание `SET available = available - ? WHERE sku = ? AND available >= ?` с проверкой числа затронутых строк. Другой вариант — `SELECT … FOR UPDATE` до проверки остатка в той же транзакции.

2. **Один запрос может создать два резерва.** При одинаковом ключе обе транзакции могут увидеть пустой результат. В таблице есть первичный ключ на `id`, поэтому обе вставки получают разные идентификаторы и проходят. Даже если исправить первую гонку, при достаточном остатке оба вызова смогут списать товар. Поиск резерва — строка 37. Схема — строка 19.

   Один вариант — `UNIQUE (customer_id, request_id)` и `INSERT … ON CONFLICT DO NOTHING RETURNING id` перед списанием. Остаток уменьшает транзакция, которая вставила строку. При нехватке товара вставка откатывается. Если вставки не было, следующий `SELECT` в `READ COMMITTED` может прочитать резерв победившей транзакции.

**Как проверить.** Запустить два вызова на отдельных транзакциях в PostgreSQL с контролируемым порядком шагов. Для разных ключей при остатке `1` ожидаем один успешный резерв. Для одинакового ключа при достаточном остатке — одинаковый `id` в обоих ответах, одну строку резерва и одно списание.

**Вопросы кандидату.** Что получат два покупателя, если оба успели прочитать остаток `1`? Если после ошибки уникальности перехватить исключение, можно ли сделать `SELECT` в той же транзакции? После SQL-ошибки нужен rollback или откат к заранее созданному savepoint. Другой вариант — обработать конфликт после завершения транзакции и прочитать резерв в новой.

## Импорт прайс-листа

Файл кандидата — `PriceListImport.java`.

### Суть кейса

Оператор загружает цены для существующих товаров. Файл должен примениться целиком. Если встречается некорректная строка, оператор получает её номер, а цены остаются прежними.

Контроллер вызывает `importPrices` на Spring-бине без внешней транзакции. Метод делегирует в `applyPrices`, который проверяет и записывает строки по порядку. Возьмём файл, где строка 2 CSV обновляет цену товара A со `100` до `120`, а строка 3 CSV содержит нулевую цену. Ожидаем ошибку в строке 3 CSV и цену `100` у товара A.

### Что не так

1. **Вызов проходит мимо транзакционного прокси.** `importPrices` напрямую вызывает `applyPrices` на том же объекте. В стандартном proxy-режиме аннотация на внутреннем методе при этом вызове не срабатывает. Первая запись фиксируется, затем метод выбрасывает ошибку в строке 3 CSV. Оператор видит корректный номер ошибки, но цена A уже `120`. Вызов — строка 29. Аннотация — строка 33.

2. **Открыть транзакцию недостаточно.** `InvalidPriceRowException` наследуется от `Exception` и является checked exception. Если просто перенести `@Transactional` на `importPrices`, при стандартных правилах Spring транзакция всё равно закоммитится. Выброс исключения — строка 37. Тип исключения — строка 50.

   Оба дефекта закрывает `@Transactional(rollbackFor = InvalidPriceRowException.class)` на `importPrices`, если контроллер вызывает этот метод через бин. Допустимо вынести запись в отдельный транзакционный бин. Если кандидат предлагает сначала валидировать весь файл, уточните, как он сохранит атомарность обновлений при ошибке уже на этапе записи.

**Как проверить.** Вызвать `importPrices` через Spring-бин на PostgreSQL. Проверить номер ошибочной строки, затем отдельно прочитать цену A. Тест не должен открывать общую транзакцию вокруг вызова, иначе она замаскирует отсутствие транзакции в сервисе.

**Вопросы кандидату.** Где открывается транзакция при реальном вызове из контроллера? Что изменится, если перенести только аннотацию? Где преобразовать исключение в HTTP-ответ? Например, в `@ControllerAdvice` после выхода из транзакционного метода, чтобы прокси успел применить правило отката.

## История заказов

Файл кандидата — `OrderHistory.java`.

### Суть кейса

Личный кабинет возвращает до 50 заказов текущего клиента вместе с позициями. Сначала идут новые заказы. Две соседние страницы при неизменных данных не должны пересекаться. В таблице около 10 млн заказов.

Клиент уже определён HTTP-фильтром. Контроллер запрашивает страницу заказов через JPA, затем в той же транзакции проходит по позициям каждого заказа и собирает DTO. На ревью интересны отдельно число запросов, порядок строк и стоимость выборки страницы.

### Что не так

1. **N+1 при сборке DTO.** Запрос загружает только заказы. `order.items.stream()` внутри маппинга обращается к ленивой коллекции. На полной странице в чистом контексте без пакетной загрузки и попаданий в кеш можно получить 51 SQL-запрос — один за заказами и 50 за позициями. Транзакция позволяет ленивой загрузке выполниться, поэтому обычный функциональный тест может увидеть правильный ответ. Чтение `items` — строка 61. Маппинг коллекции — строка 80.

   Вариант исправления — выбрать страницу заказов, одним запросом загрузить позиции по их `order_id` и собрать DTO в исходном порядке. Подойдёт и проекция, если ограничение страницы применяется к заказам.

2. **Порядок при равном `created_at` не задан.** Предложите представить 51 заказ с одинаковым временем. Запросы с `offset=0` и `offset=50` могут по-разному упорядочить равные строки. Тогда одна строка повторится, а другая потеряется даже на неизменных данных. Добавьте уникальный второй ключ, например `ORDER BY created_at DESC, id DESC`. Для глубоких страниц или изменений между запросами можно обсудить курсор по паре `(created_at, id)`. Сортировка — строка 55.

3. **В схеме отсутствует индекс под фильтр и сортировку заказов.** Индекс по `order_items.order_id` помогает искать позиции. Для заказов стоит проверить B-tree по `(customer_id, created_at DESC, id DESC)`. Тогда PostgreSQL сможет искать по клиенту и читать его заказы в нужном порядке. Само наличие `Seq Scan` в плане ещё не доказывает проблему. Схема — строка 26. Запрос — строка 52.

**Как проверить.** Посчитать SQL-запросы на полной странице, прогнать две соседние страницы на данных с совпадающим `created_at`, сравнить `EXPLAIN (ANALYZE, BUFFERS)` до и после изменения индекса.

**Вопросы кандидату.** Сколько SQL-запросов сделаем на странице из 50 заказов? Что изменится при `JOIN FETCH` коллекции вместе с `setMaxResults`? Соединение размножает строки заказа. Hibernate 7.4 с PostgreSQL может ограничить заказы в подзапросе перед загрузкой коллекции. На более ранних версиях Hibernate типичное поведение — пагинация в памяти. Попросите кандидата сказать, что он проверит в фактическом SQL.

## Подтверждение отгрузки

Файл кандидата — `ShipmentConfirmation.java`.

### Суть кейса

Склад переводит отгрузку из `READY` в `CONFIRMED`. Сервис доставки должен получить событие после успешного изменения статуса даже при перезапуске отправителя. Повторная доставка допустима. Если статус откатился, соответствующее событие появиться не должно.

`confirm` выполняет условный `UPDATE`. Если строка изменилась, он ждёт подтверждения брокера и возвращает `true`. При вызове через Spring-бин без внешней транзакции коммит происходит после завершения метода. Условие `status = 'READY'` защищает переход от повторного обновления.

### Что не так

**Событие может уйти в брокер, а изменение статуса откатиться.** В строке 27 метод обновляет статус в PostgreSQL, а в строке 33 публикует событие до коммита. Например, брокер принял сообщение, но подтверждение не дошло до приложения. `publish` выбрасывает исключение по таймауту, Spring откатывает транзакцию. Сервис доставки уже может обработать событие, хотя отгрузка в БД осталась `READY`.

**Исправление — transactional outbox.** В `confirm` после успешного `UPDATE` заменяем `publish` на `INSERT` в `outbox_events`. В записи сохраняем `event_id`, тип события и `shipment_id`. Смена статуса и запись события идут в одной транзакции. При откате исчезают оба изменения. После коммита запись доступна обработчику и сохраняется при перезапуске приложения.

Отдельный обработчик отправляет ожидающие события в брокер и отмечает их как отправленные после подтверждения. Если он упадёт между подтверждением и отметкой, повторная отправка использует тот же `event_id`. Потребитель может сохранить обработанный идентификатор в одной транзакции со своим изменением данных, чтобы обработать событие один раз.

**Как проверить.** Смоделировать откат обновления и убедиться, что записи outbox нет. Затем остановить обработчик после коммита статуса, перезапустить и проверить доставку. Отдельно остановить его после подтверждения брокера, но до отметки о доставке, и проверить повторное получение события с тем же идентификатором.

**Вопросы кандидату.** Может ли брокер принять сообщение, если `publish` выбросил исключение по таймауту? Что произойдёт со статусом отгрузки? Если обработчик outbox доставил событие дважды, как потребитель сделает свою бизнес-операцию идемпотентной?

**Дополнительный вопрос про нагрузку.** Что произойдёт, если брокер начнёт отвечать медленно? Пока `publish` ждёт ответа, транзакция удерживает блокировку строки отгрузки и занимает соединение с БД. При большом числе параллельных подтверждений может исчерпаться пул соединений. Outbox убирает сетевой вызов из транзакции изменения статуса.

## Расчёт суммы счёта

Файл кандидата — `InvoiceTotal.java`.

### Суть кейса

Сервис складывает стоимости позиций, применяет процентную скидку ко всему счёту и один раз округляет до копеек по `HALF_UP`. Цены приходят как `BigDecimal`, контроллер уже проверил входные данные.

`calculate` обнуляет поле `subtotal`, переводит цены в `double`, накапливает сумму, применяет скидку и только затем переводит итог обратно в `BigDecimal`. Оба дефекта можно разобрать без БД.

### Что не так

1. **Два запроса делят один накопитель.** `@Service` по умолчанию создаётся как singleton. Запрос A насчитал `100` и остановился перед применением скидки. Запрос B обнулил поле и насчитал `200`. Когда A продолжит работу со скидкой `10%`, он может вернуть `180` вместо `90`. Накопитель должен быть локальной переменной `calculate`. Поле — строка 16. Чтение итога — строка 24.

2. **Округление применяется к уже неточному результату.** Три единицы по `0.29` со скидкой `50%` дают точно `0.435`, ожидаемый результат — `0.44`. Через `double` получается `0.43499999999999994`, и `HALF_UP` возвращает `0.43`. `BigDecimal.valueOf(total)` в конце не восстанавливает потерянную точность. Используйте `BigDecimal` от входной цены до единственного округления в конце. Конвертация цены — строка 21. Округление — строка 25.

**Как проверить.** На примере `0.29 × 3`, скидка `50%`, сравнить результат с `0.44`. Для общего поля достаточно, чтобы кандидат указал конкретный порядок действий обоих потоков. Автоматическое воспроизведение требует контроля над порядком операций.

**Вопросы кандидату.** Что вернёт A, если B завершит расчёт между последней итерацией A и применением скидки? Можно ли считать в целых копейках? Да, если сохранить дробную часть скидки до финального округления и учесть диапазон промежуточных значений.
